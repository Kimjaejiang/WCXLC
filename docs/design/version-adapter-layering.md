# 版本适配分层设计（已定方案，暂不实现）

> 状态：**设计已确认，尚未实现**。记录在此以免丢失。
> 提出人：用户。实现优先级低于「归拢不落库重构」与「兼容性诊断页」。

## 1. 核心思路

把适配代码**按微信版本分文件**组织：

```
adapters/
  v8.0.77.kt
  v8.0.78.kt
  v8.0.??.kt   ← 新版本来了，复制一份改改
```

把「适配新版本」从 **改代码** 变成 **加文件**：

- 新版本适配：新增一个 `vX.Y.ZZ.kt`，不动老文件
- 旧版本适配不会丢：老的 `vX.Y.ZZ.kt` 原地不动
- 放弃某版本：**删掉那个 `vX.Y.ZZ.kt` 即可**，不影响其他版本

## 2. 用户已明确的两项决定（不要自作主张改动）

### 决定一：版本匹配 = 必须精确匹配

装的是微信 `8.0.79`，而仓库里只有 `v8.0.78.kt`

→ **不降级、不回退**，该功能报「不支持当前微信版本」。

（对比：另一种常见做法是「用 ≤ 当前版本的最大者」，被用户否决。）

### 决定二：隔离粒度 = 整个功能按版本分文件

不做「只把 hook 锚点放进版本文件、公共逻辑共享」的细粒度方案，
而是**整个功能整套**按版本切：

```
adapters/v8.0.78/NotificationsEvolved.kt
adapters/v8.0.77/NotificationsEvolved.kt
```

## 3. 用户已知悉并接受的后果

「精确匹配 + 整功能分文件」组合后：

1. **微信每次更新，所有功能立即失效** —— 直到为每个功能补一份新的版本文件。
   哪怕只是一个补丁位版本号变化。
2. **文件数量乘法增长**：功能数 × 版本数。
3. **维护成本从「改一处」变成「每个功能补一个文件」**。
4. 大量重复代码：本项目 hook 定位**大量依赖 `usingEqStrings(...)` 字符串锚点**
   （见 `WeDatabaseListenerApi`、`HideContactsSql` 等）。这类锚点在版本之间经常是稳定的，
   强行整体按版本切会产生成片的重复代码。

用户在看到上述后果后仍明确选择了这两项。**实现时保持原样。**

## 4. 待定 / 未验证

- **版本选择机制怎么做**，三种候选：
  - A. 编译期注解扫描生成注册表 —— **最契合现有架构**。项目已有
    `libs/common/annotation-scanner/`，正用于生成 `FeaturesProvider.ALL_HOOK_ITEMS`。
  - B. 运行时反射拼类名（`v8_0_78`）—— 简单但拼字符串易错、IDE 无法静态检查。
  - C. 手写 `when (version)` 注册表 —— 又回到改代码，但只改一处。
- **微信版本号是否连续可枚举**：存在带小版本的号（如 `8.0.78.xx`）、灰度版本。
  精确匹配语义下，「装的是 8.0.78.31 而文件叫 v8.0.78.kt」是否算匹配，需先定清楚。
- **公共逻辑能否真的完全避免重复**：需实测若干功能后才知道重复率有多高。

## 5. 与现有机制的衔接

本项目已有 `IResolveDex` + **DEX 缓存**机制（`DexCacheManager`、`FeaturesLoader`）。
引入版本分层时需要注意：

- `FeaturesLoader.loadFeatures()` 会**跳过 DEX 缓存未就绪的功能**
  （日志：`skipping <name> — incomplete cache, awaiting re-resolution`）。
  这意味着「功能没生效」有两种可能：**被版本门挡了** vs **DEX 缓存没就绪**。
- 因此本设计**依赖「兼容性诊断页」来区分这两者**，否则用户无法判断
  到底是版本不支持还是缓存没准备好。
